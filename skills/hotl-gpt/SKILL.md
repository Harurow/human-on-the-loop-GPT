# HOTL GPT

人間が目的と要件を決め、承認した範囲の仕様化・設計・実装・検証を Codex が進める。
ユーザーの最新の指示、既存の承認、ホストの実行権限を尊重する。スキル独自の確認を重ねない。

## 開始と再開

このファイルを基準に `scripts/hotl.py` と `references/` の絶対パスを解決する。
以後、CLI には対象プロジェクトの絶対パスを `--project` で渡す。CLI の契約と例は
[runtime.md](references/runtime.md) を必要時に読む。Python 3.9 以上、Git、macOS/Linux を使う。

1. 対象を特定する。親ワークスペースに `*/docs/hotl.state.json` があるなら、対象の子ディレクトリへ進む。
   複数候補で特定不能な場合だけ対象を聞く。親自体をプロジェクト化しない。
   マルチプロジェクトの指示は隣接する `hotl-gpt-pm/SKILL.md` があればそちらへ渡す。
2. 状態があれば `status` で現在フェーズ、未処理入力、停止、承認の有効性を読む。
   状況確認だけなら読み取りで回答して終える。走行中の状況質問なら回答後に作業を続ける。
   状態がなければ、新規開発が依頼されている場合だけ `init` を実行する。
   同名の既存文書や原版 HOTL の状態を上書きして初期化しない。
3. 作業再開時は `check`。要件変更を検知して終了コード 2 が返ったら、旧承認は既にリセット済み。
   差分を確認して要件フェーズへ戻る。CLI を同じ引数で無条件に連打しない。
4. 未処理入力を個別に扱い、現在フェーズの参照文書だけを読む。
   再開時は tasks.md の再開欄と対象タスク、関連 ID の要件・仕様・設計、実際の差分から復帰する。
   会話全体・全ログ・無関係なコードを先に読み込まない。不足や矛盾がある範囲だけ追加確認する。

初回は MVP を完成させてから改善を重ねる。範囲の選別は discovery.md、
優先順位・後回し候補・再開情報の運用は development.md に従う。

## 判断と事後報告

承認済みの目的・必須要件・実行権限の範囲で、安全性を確認でき、修正可能な実装方式、
タスクの分割・順序、既存基準内の不具合修正は AI が判断して進める。
任意の好みが未指定でも作業を止めず、目的に合う仮定で実装し、判断と理由を note に短く残す。
進捗・完了報告で重要な判断と影響を伝え、ユーザーから訂正があれば該当差分を修正する。
事後報告への返答は次の作業の開始条件にしない。

目的・必須要件を変える、未許可の費用・公開・外部送信を伴う、破壊的で復旧困難、
または安全性を判断する情報が足りない場合は、その判断に依存する操作だけ保留する。
先に調査・具体案・影響の整理と、独立して進められる許可済み作業を済ませ、必要な判断だけ尋ねる。
包括的な自律判断の許可を、未提示の要件版への承認や実行権限の拡大として登録しない。

## 入力を取りこぼさない

状態変更を伴うユーザーの発言は、処理前に `receive` へ渡す。
同じメッセージでも「承認」「不具合」「追加要望」「質問」は別々の intent とする。
元メッセージと順番を保ち、各 intent に戻された `I-n` ごとに解決する。
再開時は元の `source_key` を再利用し、新しいメッセージには新しいキーを使う。
秘密情報の実値はメッセージ記録・入力 JSON・ログに残さず、名前と保存先で置き換える。

| 入力 | 扱い |
|---|---|
| 停止 | `stop` を受領すると CLI が停止状態にする。実行中の長い処理も可能な安全な境界で中断し、次のタスクを始めない |
| 再開 | 明示的な再開指示を `resume` として登録して `resume`。要件承認の代わりにはしない |
| 要件の承認 | 提示した版に対する実際のユーザー発言を確認し `approve`。エージェント自身の賛成を登録しない |
| 要件の追加・削除・意味変更 | `change` として登録。`reset` を先に実行し、要件を更新してからその入力を解決し、変更後の版を提示 |
| 承認範囲内の不具合 | `bug` を登録。done なら `reopen`。修正タスクを作成し、その T-n へ `resolve` で関連付ける |
| 設計上の希望・質問 | 反映または回答後、その I-n だけを解決する。他の intent は未処理のまま残す |

承認と要件変更が混在するときは変更を先に反映し、更新版を提示する。旧版への承認を流用しない。
承認と既存基準内の不具合報告が混在するときは承認を処理できる。不具合は別 I-n のまま
修正タスクに関連付け、承認後の開発で直す。要件が変わらなければ再承認しない。
実装の改善提案は tasks.md の後回し候補を正本とし、その他の提案は `note` の proposal に記録する。
同じ本文を両方に残さず、ユーザーが採用するまで要件を増やさない。
停止の解除に新しい承認は不要。未処理の approval が古い版に対するものなら、
根拠を残して後述の runtime の `dismiss` で閉じ、現在の版への回答と混同しない。

## フェーズ

| 状態 | 参照 | 出口 |
|---|---|---|
| hearing / requirements / awaiting_approval | [discovery.md](references/discovery.md) | 提示済み要件への承認記録 |
| specification / design | [planning.md](references/planning.md) | 追跡可能な仕様・設計と検証方法 |
| development | [development.md](references/development.md) | リスクに応じた検証（通常は独立したコード・受け入れ検証）、`complete` 成功 |
| done | 新要望なら discovery、不具合なら development | 要望の性質に応じた差分更新 |

承認済み要件は formatter を含め編集しない。変更する前に `reset` を実行する。
R-n / NR-n / S-n / T-n は永続 ID。削除後に番号を詰めない。
既存成果物は差分更新する。タスク進捗の正本は `docs/tasks.md` のチェックボックスだけ。
state と log は CLI が管理し、手編集しない。`log.md` は状態から再生成できる表示専用。

## 実行環境と独立性

フェーズの委譲、コードレビュー、受け入れ検証には、利用可能ならサブエージェントを使う。
各参照文書の入力だけを渡し、会話全体を継承させない。
このホストで `collaboration.spawn_agent` が使える場合は `fork_turns="none"` とし、
モデルを指定せずセッション設定を継承する。他ホストでは公開された同等の仕組みを使う。
ツール名や能力を推測して呼ばない。ホストが委譲を禁止する場合はその制約に従う。
実装コンテキストの実際の識別子を `work.actor` に登録し、レビュー担当には別の識別子を記録する。
別の名前を付けただけの同一コンテキストを独立レビューと称さない。

development.md の限定的な説明文書修正は editorial 自己検証を使える。
独立検証が必要で、その環境がない場合も、実装・テスト・報告までは進める。
自己検証を `note` に記録して「独立検証未実施」と報告する。`review` の担当名を偽って
`complete` を通さない。後日、別のコンテキストから検証して完了できる。

質問 UI は利用可能なものだけを使う。任意の好みには非同期質問を使えるが、未回答を承認としない。
承認はユーザーの明示的な発言で取得する。既に提示版を承認していれば再質問しない。
ホストの操作許可は要件承認とは別であり、既存の権限とユーザーの許可範囲を引き継ぐ。

## 報告

フェーズ完了・タスク数件の完了・重要な問題の発見時に、成果と次の作業を短く伝える。
長時間処理中もホストの頻度に従い進捗を伝え、各タスク開始前に停止・新着入力を確認する。
通常の進捗で返答を要求しない。ユーザー判断が必要なら、具体的な差分と影響を示す。
作業の完了には development.md の Git 処理と「作業報告書」の提出を含める。
作業報告書は対象、完了状況、変更点、確認結果、Git の結果、課題・残タスク、ユーザー作業を短く示す。
スコープ外の改善案はまとめて提示する。承認済み基準を満たさないものを改善案に移して完了しない。
