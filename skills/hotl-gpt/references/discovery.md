# ヒアリングと要件承認

ヒアリングは目的・利用者・代表的な場面・成功の条件から始める。
既に決まっていることを聞き直さず、未確定部分を推測ドラフトにまとめて訂正を受ける。
解決方法が未確定なら異なるコンセプトを2〜3案提示し、選択済みならその案を具体化する。
ユーザー発案とエージェント提案を区別し、採用前の提案を実装範囲に含めない。

`docs/hearing-notes.md` に目的、利用者、シナリオ、採用・見送り、非ゴール、未確定事項をまとめる。
`transition` で requirements へ進み、`assets/requirements.md` を参考に要件書を作る。
テンプレートの記入ガイドを削除する。文書の厚さは規模に合わせる。

要件には永続 R-n / NR-n、受け入れ条件、出所を記す。
非機能は性能・費用・公開範囲/セキュリティ・データ保全・運用を検討する。
適用しないものは理由を書き、実測できない値を既定で保証しない。
実行環境と自律実行範囲（例: ローカル実装・テスト、利用可能サービス、費用上限）を明記する。
ユーザーが既に許可したことを取り消して再確認する規則は追加しない。

要件レビューは fresh context に「要件書」とこの文書の観点だけを渡す。
観点: 矛盾、ユーザー要求との区別、検証可能性、漏れ、非ゴールとの衝突。
実行条件や具体的な失敗例のない文言の好みで修正を反復しない。
初回の重大指摘を修正し、再確認は変更箇所中心の1回を基本とする。
矛盾が残るときは選択肢と影響をユーザーに示す。要件レビュー結果は note に残す。

`present` に判断用の要約を渡し、戻された sha256 の版をユーザーに提示する。
提示文は目的、機能、対象外、費用・運用上の前提、要件書へのリンク。
再提示なら「前回との差分」と費用・機能への影響を先に示す。
承認待ちの間は要件ファイルを変更しない。変更したら再提示する。

実際の承認発言を `receive` の approval として登録し、その I-n と提示ハッシュで `approve`。
「続きから」は再開であり要件承認ではない。要件変更・承認の混在は変更が先。
既存の受け入れ基準内の不具合報告は承認と独立して扱い、修正タスクへ関連付ける。
CLI は発言の意味や人間の身元を認証できないため、発言と提示版の対応はメイン担当が確認する。
承認後は仕様化へ自律続行する。

done 後の新機能は `reset` (phase=hearing) から差分ヒアリング。
既存基準の不合格は承認をリセットせず、bug と修正タスクで扱う。
