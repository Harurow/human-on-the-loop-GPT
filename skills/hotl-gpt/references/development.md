# 実装と検証

## タスクと実装

docs/tasks.md の正規行は `- [ ] T-1 内容; 関連: S-1; 完了条件: ...`。
`[ ]` 未着手、`[>]` 実行中、`[x]` 完了、`[-]` 取り下げ。
取り下げた理由は note に残し、受け入れ条件を勝手に減らさない。
末尾の有効タスクに `[acceptance]` を含む最終検証タスクを置く。
タスクには検証可能な完了条件を書く。テンプレートは assets/tasks.md。
既存進捗を生成し直さない。修正タスクは最終検証の直前へ挿入する。

最初に Git のルートが対象プロジェクトと一致することを確認する。
新規なら通常の許可範囲で git init。親リポジトリに所属する既存コードの場合は入れ子にせず、
独立した作業場所を用意する方針を決める。この版の snapshot は独立リポジトリが必要。
秘密情報、依存キャッシュ、ビルド出力は .gitignore に含める。
docs/.hotl.lock と docs/.hotl-tmp-* も無視する。state、log、検証証拠は保存対象。
勝手な作者設定・既存変更の破棄・公開は行わない。

実装に入る各コンテキストは `work` に実際の識別子と作業内容を登録する。
最終検証後の修正時にも必ず work を再実行し、既存の検証記録を無効にする。
タスク進捗は個別に更新し、同じ変更単位の軽微なタスクはまとめて検証する。
同一成果物・同一環境に対する合格済みのコマンドは、変更・失敗・新しい懸念がなければ再実行しない。
局所確認を先に行い、必要な全体テスト・ビルドは変更がまとまってから実施する。
リポジトリが必須とするチェックは省略しない。結果・分類理由・判断は一つの note にまとめてよい。
同じ内容を tasks、note、lessons に重複して書かない。
レビューは編集ごとではなく、次の変更リスクに合わせて行う。変更行数で軽微と判断しない。
初回開発・要件変更は独立した最終検証が必要。不明な影響は通常以上として扱う。

| 変更 | タイミングと確認範囲 |
|---|---|
| 説明文書の誤字など、意味・挙動が変わらない修正 | 後述の限定条件を満たせば editorial 自己検証で完了 |
| 余白・色・表示文言などの微調整 | 調整をまとめ、最後に独立担当1人が差分と対象画面の操作を確認 |
| 局所的な不具合修正・小機能 | 一まとまりの実装後に独立レビュー1回。関連テストと影響する受け入れ基準を確認 |
| 認証・権限・課金・データ更新・共有契約 | その変更に依存する実装を広げる前に個別レビュー。完了時も関連する回帰・受け入れ検証 |
| 新規開発・広範囲の変更 | 主要操作の早期確認と全受け入れ基準の最終検証 |

分類と理由は既存の note に短く残す。分類用の追加エージェントや台帳は作らない。
軽微・局所変更では code/acceptance を同じ独立担当にまとめて依頼し、両役割の結果を登録する。
担当・対象ハッシュが同じなら、役割ごとの確認結果を一つの証拠ファイルにまとめ、
両方の review から参照してよい。登録後の証拠は追記せず、必要なら新版を作って再登録する。
レビュー修正後は同じ独立担当を再利用し、前回の指摘、差分、影響先だけを再確認する。
確認済み範囲と根拠を報告へ引き継ぐ。無関係な全体再読・テストの再実行は行わない。
新しい影響や不合格が見つかった場合は範囲を広げる。実行した検証と以前の証拠の再利用を区別する。
修正後の再確認は1回を基本とし、具体的な未解決不具合があれば継続する。
好みや範囲外の改善案だけで反復しない。

新規開発・主要導線の変更では、主要操作が通る最小版で一度、利用者のシナリオを実行する。
完了済み製品の局所修正では、影響する操作の確認に絞る。
画面の確認は実際の対象環境で行う。新規UI・レスポンシブ構造の変更では対象の
モバイル/デスクトップを確認し、局所修正は影響する画面・表示幅・操作に絞る。
画面に影響しない変更で、スクリーンショットを撮り直すためだけにブラウザーを起動しない。
この早期確認は追加承認のゲートではない。範囲内の使いにくさは自律修正し、追加機能は提案へ。
必要な秘密情報や権限がなくても実行できるタスクは進める。
同じ失敗への再試行は方法を見直し、受け入れ検証が3回失敗したら証拠と次の具体策を報告する。
不合格のまま done にしない。回数をリセットするだけの再試行を行わない。

## 説明文書だけの自己検証

例: done 後の README 誤字修正は既存基準内の bug として receive → reopen し、
修正タスクへ resolve して work を登録する。要件の再承認は不要。

独立検証で完了した版があり、その版からの累積差分が README.md、docs/help/**/*.md、
docs/guide/**/*.md と tasks.md の進捗記帳だけなら、独立レビューを省略できる。
AGENTS.md / SKILL.md、要件・仕様・設計、コード（コメントを含む）、設定は対象外。
文書でも受け入れ基準・操作手順・コマンド・権限・費用の意味を変える修正、実行時に読み込む
文書の変更は対象外。表示の意味、リンク先、生成物への影響も確認し、不明なら通常レビュー。

メイン担当が基準版からの累積差分を確認し、対象文書の自己確認と必要なリンク・表示確認を行う。
最終タスクも含めて記帳を終え、snapshot を取得する。証拠には基準、変更ファイル、
意味・挙動が変わらない根拠、確認結果、独立レビュー省略を記し、review の role=editorial、
実際の実装担当ID、no_behavior_change=true、reason と証拠を登録して complete。
CLI の入力例は [runtime.md](runtime.md)。独立検証の合格と称さず、最終報告にも省略を明示する。

CLI は対象パスと最新ハッシュを確認するが、文書の意味は判定しない。適用判断は担当の責務。
新規開発、基準版のない旧状態、要件再承認後、レビュー不合格後は独立検証を必要とする。
自己検証を繰り返しても基準版は更新しない。コード変更を小分けにして省略条件を通さない。

## 最終検証の順序（独立レビュー）

1. 修正タスクを含む実装が完了し、各 I-n が回答済み/反映済み/タスクへ関連付け済みであることを確認。
2. docs/tasks.md の最終検証を `[>]` にしたまま、独立した受け入れ担当が実際に検証する。
   コードレビューの最終担当も別コンテキスト。両者に同じ担当を使うことは可能だが、実装担当は禁止。
3. 担当からの合格を受けて最終検証を `[x]` にする。これは進捗記帳であり実装変更ではない。
4. `snapshot` で最終ファイル集合のハッシュを取得し、各検証担当に返す。
   担当は前回確認からの差分がタスクのチェックのみであることを確認し、
   その最終ハッシュ、結果、実行コマンドと出力要約、基準別の合否を docs/reviews/ に保存する。
   スナップショット前後にコードが変わった場合は、その変更を検証してから合格を出す。
5. メイン担当が各報告を `review` で登録する。code と acceptance の両方が必須。
   CLI は最新の対象ハッシュ、証拠の内容ハッシュ、実装担当との不一致を確認する。
6. `complete`。入力漏れ・未完了タスク・古い証拠・不合格が残れば拒否される。

review の記録は検証の実行を代行しない。実行していない確認は「未実施」とする。
review の途中で修正が必要なら担当は指摘を返し、メイン担当が work → 修正 → 再検証。
レビュアー自身が修正したら、その担当も writer として登録し、別担当に検証を引き継ぐ。
証拠保存先 docs/reviews/ は対象ハッシュから除くが、登録した証拠ファイル自体は別途ハッシュで保護する。
その他の gitignore 対象は対象ハッシュに入らないので、アプリの実コードを無視対象にしない。

## 渡す入力

会話全体を渡さず、差分・関連基準・必要な依存先に絞る。既存担当を継続利用できるなら
変更点だけを追加する。報告は重大度付きの具体的指摘、確認範囲、検証結果、未確認範囲に絞る。

| 役割 | 入力と確認範囲 |
|---|---|
| コードレビュー | diff、関連仕様・設計、タスクの完了条件、費用・セキュリティ前提。最終段階では実装全体の確認も許可 |
| 受け入れ検証 | 要件の受け入れ基準と前提、リポジトリ、起動手順。実装者の「合格したはず」という説明は渡さない |
| UX | 利用者・シナリオ・成功条件と動く成果物。コードを読まず主要操作を実行 |
| セキュリティ | リポジトリ、公開範囲、認証・データ保全の前提。秘密の実値を読ませない |

初回の受け入れ担当は機能基準に加え、ドキュメントの対応、未処理指摘、性能、費用、データ保全、
運用、セキュリティ前提を確認する。局所修正では前回の証拠と影響確認を根拠に、
変化のない項目を引き継ぐ。性能・課金経路・依存・環境・前提が変わった項目は再確認する。
性能の数値基準は実測。課金呼び出しは使用量と頻度から費用を計算し、測れない部分は明示する。
外部課金がなければその旨を記録する。
初回開発や主要導線・アクセシビリティの変更では UX、初回の外部公開・認証・機密データの導入や
その境界の変更ではセキュリティ担当を分離し、ux/security の review も登録する。
既存画面の微調整は受け入れ担当が対象画面を確認する。公開済みという理由だけで、
無関係な修正にセキュリティ担当を毎回追加しない。追加担当を省く理由は受け入れ報告に短く記す。
CLI は通常 code/acceptance、限定的な説明文書修正では editorial を要求する。
条件付きレビューの適用判断は要件と担当の責務。

## 完了と再開

次回に役立つ新しい実測結果がある場合だけ docs/lessons.md に記録する。
成果物の文書は最終レビューより前に記入を終える。報告のためだけの追加文書は作らない。

CLI の complete は成果物の検証完了。作業全体の完了報告は以下の Git 処理まで済ませてから行う。
Git 管理されている場合は、変更差分とステージ対象を確認し、この依頼の変更をコミットする。
他作業の変更や秘密情報を一括で追加しない。origin が設定されている場合は push まで行う。
現在のブランチと追跡先を確認し、対応する origin のブランチへ通常の push を行う。
追跡先がない作業ブランチは origin の同名ブランチへ push して追跡を設定する。
ユーザーによる Git 操作の制限は優先する。作者情報を勝手に設定せず、force push はしない。
Git 未管理・origin なしの場合は該当処理を対象外と報告する。
この規則のためだけに既存フォルダを git init したり、origin を推測して追加したりしない。
認証・競合・保護設定などで実行できなければ、成果物の検証完了と Git 処理未完了を区別し、
失敗した処理、理由、残タスク、必要なユーザー作業を報告する。未実施を完了と称さない。
コミット・push だけではレビューを再実行しない。フック等で成果物が変われば完了を報告せず、
再開手順に従って開発フェーズへ戻し、work → 再検証してから変更をコミット・push する。

最終報告は「作業報告書」として会話内に提出し、対象を明記して次の項目を短くまとめる。
別ファイルはユーザーが求めた場合だけ作成する。該当しない課題やユーザー作業は「なし」と明記する。
- 作業状況: 完了、または実施できなかった作業が残ること。
- 変更点: 利用者にとって何が変わったか。
- 確認結果: 実施した検証、必要なら省略したレビューと理由。
- Git: コミット・push の結果、または対象外の理由。
- 課題・残タスク: 本来必要だが実施できなかったものと理由。
- ユーザー作業: 必要な操作と目的。なければなし。
起動・利用方法が変わった場合だけ手順を添える。開発サーバーが必要なら起動して URL を示す。
