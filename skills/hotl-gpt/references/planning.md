# 仕様化と設計

既存基準内の修正では影響のない要件・仕様・設計を読み直したり書き換えたりしない。
仕様化・設計が必要な小規模変更では、同じ作成担当が両方を順番に扱ってよい。
別担当を起動するためだけの引き継ぎを省く。新規・広範囲・高リスク変更では以下の分離を基本とする。
フェーズ順と成果物の対応確認は維持し、最終独立検証は作成担当と分ける。

仕様化には、承認済み requirements.md と既存 spec.md（あれば）、
変更した R-n/NR-n の要約と、この文書の仕様化手順だけを fresh context に渡す。
出力は docs/spec.md。会話履歴や判断ログを丸ごと渡さない。

各 S-n に関連要件、入力、出力、失敗時の挙動を書く。
画面/CLI/API の外形、保存すべきデータ、非機能制約と前提を含める。
R-n/NR-n と S-n の対応表を埋め、要件に対応しない仕様と未対応要件がないか検算する。
矛盾が要件に由来するときはメイン担当へ返し、reset 経由で扱う。
仕様完成後 `transition` (phase=design)。

設計には spec.md と既存 design.md（あれば）、変更 S-n の要約、
この文書の設計手順だけを別の fresh context に渡す。出力は docs/design.md。
既存コードを使う場合、対象モジュールと依存定義の読み取りも明示的に許可する。

設計は技術選定の理由と代替案、モジュールと S-n の対応、データ構造、失敗時の復旧、
起動・運用方法、検証コマンドを示す。既存のフレームワークとツールを優先する。
formatter/lint/型検査/テスト/ビルド/依存検査の必要性を判断し、該当コマンドを記す。
凍結した requirements.md を自動整形対象にしない。
同じ要件内の仕様・設計の修正は理由を記録して続ける。

全 S-n がモジュールと検証方法に割り当てられたら `transition` (phase=development)。
文書を厚くするためだけの節や別管理台帳は作らない。
