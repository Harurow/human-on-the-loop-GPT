# 最新情報の正本と状態

## 一か所に書き、一覧は生成する

|情報|正本|他の場所への記載|
|目的・受け入れ条件|docs/requirements.md の R-n / NR-n|本文を再掲せずIDを参照|
|振る舞い・入出力・失敗時の扱い|docs/spec.md の S-n|関連R/NRを記載。要求の言い換えを重ねず実現仕様を書く|
|設計理由・担当モジュール|docs/design.md|S-nへの参照。仕様本文を複製しない|
|未着手・作業中・実装済み・中止|docs/tasks.md のT-nチェック欄|状態を別JSONや再開メモに手で複写しない|
|承認・入力・照合版・レビュー記録|CLI管理のhotl.state.json|status/traceで読む。手編集しない|

`trace` は要件ごとの仕様ID、タスクIDと進捗を、その都度正本から生成する。保存したJSONを新しい編集用台帳にしない。
`[x]` は実装済みという記帳であり、検証済みや承認済みの意味ではない。検証の鮮度は対象スナップショットと証拠ファイルのハッシュから別表示する。承認は現行の要件文書全体に対するもの。要件単位の部分承認を新たに推測しない。

## 機械的に照合できる書き方

定義はそれぞれの正本で1回だけ書く。IDは変更・取消でも使い回さない。現時点のパーサーが扱う形式は次のとおり。

```markdown
# 要件
- R-1 入力文字数を確認できる。受け入れ条件：空欄は0。
- NR-1 データを外部送信しない。

# 仕様（別ファイル spec.md）
- S-1 (R-1,NR-1) 入力の変更時に端末内で文字数を計算する。

# タスク（別ファイル tasks.md）
- [>] T-1 文字数表示; 関連: S-1; 完了条件: 空欄と通常入力を検証
- [ ] T-2 [acceptance] 独立検証; 関連: S-1; 完了条件: 受け入れ条件を確認
```

要件・仕様は `## R-1 ...`、`R-1: ...` も可。コードブロック内の例は定義として数えない。タスクは既存のチェック形式を使う。表のセルにあるIDだけを定義にしない。本文の自由な日本語を解析してIDを補完しない。

traceは重複ID、不明ID参照、仕様のない要件、関連要件のない仕様、関連タスクのない仕様、関連要件/仕様のない有効タスクを返す。文言が違う同義の重複、要件の取りこぼし、実装の正しさは判定しない。そこは元の入力との照合と独立レビューで確認する。

## 更新から再開まで

1. 新しいユーザー入力はreceiveで個別に記録する。採用・未採用を区別する。
2. 要件の意味を変えるなら既存手順どおりresetして正本を更新。仕様・設計・タスクへの影響を辿る。既存の実行許可を新しい版への正式承認として登録しない。
3. T-nを作業中にしてから着手し、実装と必要なテストが終わったらチェックを更新する。仕様が変わった場合は過去の実装チェックをそのまま信用せず、影響を確認して必要な項目を作業中へ戻す。
4. `trace` で構造を確認し、ユーザー入力から文書までの意味をレビューする。整合性を確認した担当が `align` に実際の担当IDと確認範囲を登録する。
5. 再開時はtraceを再生成する。`needs_reconciliation`なら前回の照合版から変更されている。承認・実装済みチェック・古い証拠で押し切らない。関連差分を照合する。

alignは文書内容やチェック状態を保存せず、その文書全体のハッシュを記録する。細かなチェック更新でも再照合になる保守的な方式。意味の確認を自動で済ませるコマンドではなく、入力の回答や承認を代行しない。構造問題がある場合は記録を拒否する。停止中のalignも拒否する。

## 既存プロジェクトへの導入

まずtraceだけを実行し、現状の不足を確認する。既存IDや文書を自動書換えしない。参照の欠落は実際の仕様から確認して補い、確認不能な項目を無理に「対応済み」にしない。
初回alignが成功すると、以降completeには現在の文書版の照合が必要になる。旧状態を強制初期化したり、全タスクを未着手へ戻したりしない。

この仕組みは「記録した情報の構造・鮮度」を確認するもの。常駐して会話を取り込む機能ではないので、入力記帳と正本更新を省くと完全には残らない。完全性の保証ではなく、欠落を発見・修正できる運用として使う。

## HOTL自身を改善する

実案件で記録漏れ・誤った再開・古い証拠の流用が起きたら、何が正本から欠けたかを特定する。
一時プロジェクトに最小の再現例を作り、機械的に判定できる問題は回帰テストとCLIへ、意味判断の問題はレビューの入力・確認基準へ反映する。
手順を増やす前に、既存の正本を直すだけで済むか検討する。変更後は実際に別プロセス／別コンテキストから復元できるか確認し、実行した範囲と残る限界をvalidationに記す。
