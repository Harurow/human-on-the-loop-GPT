# HOTL GPT PM

ワークスペース直下の `*/docs/hotl.state.json` を都度読み、framework が
human-on-the-loop-GPT のプロジェクトだけを一覧にする。集計ファイルは保存しない。
原版の状態や壊れた JSON は別形式/読取エラーと表示し、上書きしない。
ワークスペース直下にはプロジェクトの state を作らない。

名前・会話から対象を確定し、特定できない場合だけ質問する。
承認の発言を別プロジェクトへ推測転送しない。質問に添えた対象名を引き継ぐ。
新しいプロジェクトは直下に独立ディレクトリを作り、名前をユーザーに知らせる。
名前の衝突時に既存ディレクトリを初期化しない。

対象へ隣接する `hotl-gpt/SKILL.md` を適用する。
ヒアリングと承認はメイン担当が行う。承認済みの自律区間は、利用可能なら
プロジェクトごとにサブエージェントへ委譲する。モデル設定は継承する。
入力はスキルの絶対パス、対象ルート、現在フェーズ、必要な成果物、未処理 I-n のみ。
会話全体を継承させず、同じプロジェクトへ書く担当は同時に1体とする。
サブエージェントは各タスク開始前と長い処理の前後に status を確認する。
フェーズ完了または数タスク完了で進捗を返し、継続可能なら次の区切りへ進む。

ユーザーの新着指示は対象プロジェクトの CLI receive で直接登録し、I-n を担当へ伝える。
PM は走行中担当のコード・tasks・要件を編集しない。CLI コマンド同士はロックで直列化される。
停止は stop を登録し、可能なら担当へ割り込みも送る。待機中なら次の担当を起動しない。
停止の反映状況を「受領」と「実際に停止」を区別して伝える。
メッセージが複数の指示を含む場合は hotl-gpt と同様に分解する。

担当が途中で終了しても state と成果物から再開する。
動いている可能性のある担当がいる間は代わりを起動しない。
最終受け入れ検証は実装担当と別のコンテキストへ渡す。
子エージェントがさらに委譲できなければ PM に戻し、PM が新しい検証担当を用意する。
委譲できない環境では順番に実装を進め、独立検証の未実施は明示する。

進捗表示は各プロジェクトの名前、フェーズ、tasks の完了数、未処理指示、人間に必要な対応。
破損状態のプロジェクトが1件あっても、他のプロジェクトの一覧と作業は続ける。
一つの確認待ちで他のプロジェクトの完了報告を保留しない。
CLI のロックは短い状態更新だけを守る。複数の独立セッションによる同一プロジェクトの
コード編集を排他する仕組みではないため、その運用はこの版の対象外。
